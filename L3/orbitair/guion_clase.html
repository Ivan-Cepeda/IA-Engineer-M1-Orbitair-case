Antes de empezar

La idea que ordena todo

OrbitAir quiere que un LLM haga la primera atención: leer la consulta del pasajero, decidir a qué equipo va y responder algo útil. El código se escribe en el orden en que aparecen las decisiones: primero cómo se llama al modelo, después qué se le pide, al final qué se acepta como respuesta.

Las tres clases repiten un mismo patrón: lo que varía y viene desordenado se encierra detrás de algo fijo. Ese “algo fijo” es un contrato, y cada clase lo hace más fuerte.

Clase 1 · llm.pyUn contrato de forma

Cada respuesta del SDK se traduce a LLMResponse: siempre los mismos campos.

Clase 2 · triage.pyUn contrato pedido

El prompt le pide al modelo un formato fijo (CATEGORIA: x) y el código lo lee.

Clase 3 · contrato.pyUn contrato garantizado

El schema se exige en la llamada y Pydantic lo verifica después.

llm.py ──► triage.py + prompts/ ──► contrato.py ──► app.py cómo llamo qué le pido qué acepto quién lo usa (Clase 1) (Clase 2) (Clase 3) (Clase 3) Regla: cada archivo usa al anterior; ninguno usa a uno posterior.

1.2contrato

El contrato de respuesta: LLMResponse

@dataclass
class LLMResponse:
    text: str
    input_tokens: int
    output_tokens: int       # incluye thinking: también se cobra
    thinking_tokens: int
    latency_s: float
    cost_usd: float
    finish_reason: str       # "STOP" | "MAX_TOKENS"
    ttft_s: float | None = None
Por qué

Se escribe antes que la llamada. La respuesta cruda del SDK es incómoda (usage_metadata, enums, candidatos). El resto del proyecto solo ve estos campos.

Pregunta

“¿Qué necesita saber OrbitAir de cada respuesta?” Dejar que la clase arme la lista. ¿Por qué cost_usd viene adentro? Para que nadie más tenga que saber la fórmula.

1.3llamar

La llamada: ask()

def ask(prompt, system="", temperature=0.2, max_tokens=300, **extra):
    t0 = time.perf_counter()
    r = client.models.generate_content(model=MODELO, contents=prompt,
            config=_config(system, temperature, max_tokens, **extra))
    return _armar(r, time.perf_counter() - t0)
Por qué

_config() arma los parámetros (system, temperature, max_output_tokens, thinking). _armar() traduce el usage a LLMResponse. **extra deja pasar opciones que se usan en la Clase 3.

Error a anticipar

Medir la latencia con el print adentro del cronómetro. El cronómetro va solo alrededor de la llamada.

1.5costo

Costo desde el usage, y dos experimentos de sampling

PRECIOS = {"gemini-3.1-flash-lite": (0.25, 1.50)}   # USD por 1M (input, output)

def calcular_costo(input_tokens, output_tokens, modelo=MODELO):
    precio_in, precio_out = PRECIOS[modelo]
    return input_tokens / 1_000_000 * precio_in + output_tokens / 1_000_000 * precio_out
Por qué

El costo sale de los tokens que informa la API, nunca de una estimación. El output vale 6 veces más que el input.

Experimentos

temperature 0 contra 1: ¿el mismo pedido da lo mismo? max_tokens=20 con la consulta larga: el modelo corta a mitad de frase, no resume.

1.6stream

Streaming y TTFT

for chunk in client.models.generate_content_stream(model=MODELO, contents=prompt, config=...):
    if chunk.text:
        if ttft is None:
            ttft = time.perf_counter() - t0     # lo que percibe el pasajero
        partes.append(chunk.text)
    ultimo = chunk                              # su usage es el total
Por qué

Separa la latencia percibida (primer token) de la latencia real (respuesta completa). En un chat, la percibida es la que importa.

Detalle de Gemini

Cada chunk trae el usage acumulado. Hay que quedarse con el del último, no sumarlos.

Corrida real
TTFT 0.55s · total 0.83s · USD 0.0001470
1.7reintentos

Reintentos con backoff exponencial

def with_retry(fn, max_intentos=4):
    for intento in range(max_intentos):
        try:
            return fn()
        except errors.APIError as e:
            reintentable = e.code == 429 or e.code >= 500
            if not reintentable or intento == max_intentos - 1:
                raise
            espera = _espera_sugerida(e) or (2**intento + random.uniform(0, 1))
            time.sleep(espera)
Por qué

Un 429 (límite de uso) o un 5xx se arreglan esperando. Un 400 no se arregla solo. Si Google indica cuánto esperar (RetryInfo), esa espera manda.

En clase

Con la key gratuita es fácil ver un 429 real. Si aparece, es la demo: mostrar el mensaje de espera.

Por qué

2.4medir

Evaluar todas las versiones

def evaluar(version):
    for c in consultas:
        categoria, r = clasificar(c["texto"], version)
        aciertos += categoria == c["categoria"]
        costo += r.cost_usd
Por qué

Un prompt se elige con datos: exactitud contra las etiquetas y costo por consulta. Cada versión es un archivo nuevo; nunca se edita la anterior.

Clase 3 · Salidas estructuradas y function calling

contrato.py + app.py: qué se acepta

Archivos: contrato.py, app.py, prompts/triage_v5.txtDemo: python clase3.py

El código que viene después del modelo necesita certezas: categoria == "reembolsos" exige ese texto exacto y confianza < 0.6 exige un número. El contrato es la frontera entre la parte probabilística (el LLM) y la parte determinista (todo lo demás). Se escribe en este orden: primero se muestra el problema, después el contrato, después cómo se exige y cómo se recupera.

3.1problema

Modo JSON: sintaxis sí, estructura no

ask(texto, "Devuelve un JSON con categoria y confianza",
    response_mime_type="application/json")
Por qué va primero

Muestra el problema antes de la solución: pedir JSON garantiza que se pueda parsear, no que sea correcto.

3.2débil

Contrato débil: corre sin errores y no protege

class TriageContratoDebil(BaseModel):
    respuesta: str
    confianza: float
    categoria: str
    acciones: list[str]
Por qué se escribe

Para que se vea que “no tira error” no significa “valida”. Pydantic solo revisa el tipo, no los valores permitidos.

3.3fuerte

Contrato fuerte: tipo + dominio

ACCIONES = ["derivar_agente", "pedir_num_reserva", "informar_politica",
            "iniciar_reembolso", "sin_accion"]
CategoriaValida = Literal[tuple(CATEGORIAS)]     # sale de la lista de la Clase 2
AccionValida = Literal[tuple(ACCIONES)]

class TriageContrato(BaseModel):
    respuesta: str = Field(min_length=1)
    confianza: float = Field(ge=0.0, le=1.0)
    categoria: CategoriaValida
    acciones: list[AccionValida] = Field(min_length=1)
Por qué

Cada restricción cierra una puerta: texto vacío, confianza fuera de 0–1, categoría inventada, lista de acciones vacía. Las categorías se derivan de CATEGORIAS: si se agrega una, el contrato se actualiza solo.

3.4tool call

Tool calling: exigir la forma en la llamada

TOOL_SCHEMA = TriageContrato.model_json_schema()      # el molde sale del contrato

herramienta = types.Tool(function_declarations=[types.FunctionDeclaration(
    name="clasificar_consulta", description="Registra la clasificación…",
    parameters_json_schema=TOOL_SCHEMA)])

config = types.GenerateContentConfig(
    tools=[herramienta],
    tool_config=types.ToolConfig(function_calling_config=types.FunctionCallingConfig(
        mode="ANY", allowed_function_names=["clasificar_consulta"])),
    automatic_function_calling=types.AutomaticFunctionCallingConfig(disable=True))

args = r.function_calls[0].args                        # ya es un dict
Por qué

La función no existe en Python: es un formulario que el modelo está obligado a llenar. mode="ANY" con un solo nombre le impide responder en texto. disable=True evita que el SDK intente ejecutar algo.

Pregunta

“¿Qué línea de v2–v4 sobra ahora?” “Responde SOLO con la categoría” contradice al schema. Por eso esta clase usa triage_v5.txt.

3.5reintento

Reintentos que dicen qué falló

for intento in range(1, max_intentos + 1):
    if error_previo:
        system += f"\n\n(Tu respuesta anterior fue inválida: {error_previo}. Corrígela.)"
    r = ask_tool(texto, system)

Por qué

Repetir la misma llamada es apostar al azar. Decirle al modelo qué falló es información nueva. El error va al system prompt porque es una corrección de la instrucción, no un dato del pasajero.

Conexión con la Clase 1

Es la misma idea que respetar el RetryInfo de Google: no reintentar a ciegas, usar lo que se sabe del fallo. Para la demo, "simular_error": True rompe el primer intento.

3.6errores

Errores tipados

class ConsultaInvalidaError(Exception): ...   # texto vacío: error de quien llama
class ContratoInvalidoError(Exception): ...   # se agotaron los reintentos

if not texto.strip():                         # antes de gastar una sola llamada
    raise ConsultaInvalidaError("La consulta no puede estar vacía.")
Por qué

No todos los errores merecen el mismo trato. Una consulta vacía no se arregla reintentando; un contrato inválido quizás sí. Nombrarlos permite decidir.

3.7API

La API: cada error, su código HTTP

@app.post("/triage")
def triage(consulta: ConsultaIn):
    try:
        return clasificar_validado(consulta.model_dump()).model_dump()
    except ConsultaInvalidaError as e:
        raise HTTPException(400, detail=str(e))   # revisá lo que enviaste
    except ContratoInvalidoError as e:
        raise HTTPException(502, detail=str(e))   # era válida, no pude procesarla
Por qué es tan corta

Todo el trabajo ya está en las capas de abajo. La API solo traduce excepciones a códigos. Quien la consume sabe si tiene sentido reintentar (502) o no (400).
